# GridNet: a layout model that learns its own features (2026-10-23)

## Question

The tree model learns from hand-made features (`extract/model/features.py`).
Trained on the LLM teacher's labels, it gains little: the labels are 98% right,
but its fresh-test score only moves from 130 to 132 out of 150
(`docs/llm-teacher-2026-10-23-pilot.md`).

Does a model that learns its own features from the raw character grid do
better?

## The model

[`ml/train_grid.py`](../ml/train_grid.py) defines GridNet, about 279k
parameters. It treats the capture as a grid of characters, lines by columns.

- **Along a line:** dilated convolutions. Each of the 4 layers sees about 10
  characters either side.
- **Down a column:** attention over every line at that position. This is how
  it can see a gutter, or a header word sitting over its values.
- **Heads:** one start probability per field-start candidate, and one role per
  line from a small transformer down the lines.
  - These are the same outputs as the trees, so the decoder, the scoring and
    provost's runtime would not change.
- **Training:** AdamW with a one-cycle schedule. It keeps the epoch with the
  lowest loss on held-out tool families.
- **Augmentation:**
  - digits are redrawn, and some letters (case kept);
  - one gutter is widened in every line;
  - lines are indented.
- **Synthetic layouts:** optional, from `ml/synth.py`.
- **Hybrid (optional):** the trees' 49 candidate features are added as an
  input at each candidate cell.
- **Capture-time version:** [`extract/model/gridnet.py`](../extract/model/gridnet.py)
  is the same forward pass in numpy, without torch.
  - It matches torch to within 1e-6 (`ml/export_grid.py` checks this).
  - The float16 weights are about 0.5 MB.
  - It takes 0.05 s for a 10-line capture and about 1.3 s for 100 lines on a
    loaded 4-core machine.
  - It is **not wired into provost and not shipped**.

## Measurement (development only)

The test is fold 0 of the same 5-fold, by-tool-family split as
`crossval.py`. Every model learns from the LLM labels of the other four
folds.

The yardstick is how often a line's split matches the LLM label, on all 3,163
held-out lines that have fields. The LLM labels are 98% right against the hand
labels, so this is a large, nearly-clean answer key. The 48 gold lines in the
fold are too few to separate the models.

| model | matches LLM labels (3,163 lines) | gold (48 lines) |
|---|---:|---:|
| engine | 81.4% | 32 |
| trees (hand-made features), LLM labels | 82.9% | 32 |
| GridNet, no augmentation | 78.1% | 33 |
| GridNet, augmentation + 1,500 synthetic | 79.3% | 32 |
| GridNet hybrid (+ the trees' features) | 81.2% | 34 |
| **trees and GridNet (augmented) averaged** | **83.5%** | **36** |
| trees and GridNet hybrid averaged | 83.5% | 34 |

The fresh hand-labelled test set was not used. It is kept for a model that is
a candidate to ship. The unaugmented first run printed 35 fold-0 fresh-test
lines once (GridNet 26, trees 32), and they were not used after that.

## What it says

**Learning its own features loses to hand-made features at this data size.**
All three variants show the same curve:

- training loss falls to about 0.1;
- loss on unseen tool families bottoms out near 0.65–0.70 by epoch 5–8;
- after that, the model memorises the training tools.

Augmentation and the hybrid input each narrow the gap. Neither closes it. The
corpus has about 3,000 captures, most of them under 10 lines, which is little
for a transformer to learn layout from scratch.

**The two models make different mistakes.** Averaging them beats either one,
by +0.6 points on the large yardstick and +4 on gold. That isn't enough to
justify a numpy dependency and a second model in provost.

**The bottleneck is data, not the model.** The students reach about 83% of the
teacher's labels, where the teacher itself is at 98%. The errors are real
student errors: a missed first column, merged counters, a timestamp cut in
two.

## More data: 297 Claude-written format generators (2026-10-25)

Twenty Claude helpers in the session (no API) each wrote 15 generators for
one domain: networking, storage, databases, cloud, orchestration, CI,
package managers, monitoring, defensive security, language runtimes,
hardware, VCS, media, scientific/HPC, business reports, Windows, macOS,
IoT/telecom, web, and other services.

- **What a generator is:** each one imitates one real tool's output. It
  varies rows, optional columns, value lengths and empty cells, and labels
  every line as it writes it, following the same guide as the LLM labels.
  Code is in `ml/gen/tools/`, the builder in `ml/gen/lib.py`.
- **Checks** (`ml/gen/run.py`):
  - every sample passes `ml/llm/check.py`;
  - a generator is refused if its tool family is already in `tests/corpus/`,
    so cross-validation and the hand-labelled sets stay clean.
- **After deduplication:** 297 generators. At 12 samples each that is 3,564
  samples (`ml/data/gen.jsonl`, regenerated by `run.py -n 12`).

### Fold 0, 3,163 held-out lines, how often a split matches the LLM labels

| model, training data | match | gold (48) |
|---|---:|---:|
| engine | 81.4% | 32 |
| trees, LLM labels | 82.9% | 32 |
| trees, LLM labels + generated (12/tool) | 83.1% | 34 |
| trees, LLM labels + generated (40/tool) | 81.3% | 33 |
| **trees, LLM labels + synth.py layouts** | **83.3%** | **40** |
| GridNet, LLM labels + synth | 79.3% | 32 |
| GridNet, LLM labels + generated + synth | 80.1% | 34 |
| trees and GridNet (generated + synth) averaged | 83.6% | 36 |

**The generated data helps the grid model a little (+0.8 points) and the
trees not at all.** At 40 samples per tool it outweighs the real captures,
and the trees learn the generators' habits. GridNet's validation loss rises
with it, so imitations written from memory are not close enough to real
captures to fix its overfitting.

### Full 5-fold test of the best single setup, scored once on the fresh test set

The setup is trees trained on the LLM labels plus `synth.py` layouts. It was
chosen on fold 0 above, before the fresh test set was looked at.

| | fresh test (150) | gold (300) | gold, random lines | gold, hard lines |
|---|---:|---:|---:|---:|
| shipped model (engine labels, `--clean 0.05 --fix-labels`) | 130 | 194 | 117 | 77 |
| trees, LLM labels + synth | 131 | **219** | 122 | **97** |
| engine | 126 | 193 | 120 | 73 |

Command:

```bash
crossval.py --train-corpus ml/data/corpus-llm.jsonl --extra ml/data/synth.jsonl --decode
```

The fresh test set has now been scored for the shipped model and for four
LLM-trained variants. All of them land at 129–132, which is within noise for
150 lines.

### Where this leaves the layout model

- **The LLM labels help on hard lines and are neutral on typical lines.**
  On gold, they gain 20 lines out of 150 on hard lines and about 5 on random
  lines. The fresh test barely moves.
- **No student gets close to the teacher.** The best reaches about 83% of the
  LLM's splits on held-out families, where the LLM itself is 98% right
  against the hand labels.
  - Most remaining errors are under-splitting: 298 lines miss a start, 168
    have an extra one, 61 have both.
  - A first-token rule makes things worse (77.4%), because the LLM labels
    leave out leading decoration (`->`, glyphs).
- **Candidate change:** ship the LLM-trained trees as the opt-in `--model`.
  - **For:** +25 gold lines, almost all on hard lines.
  - **Against:**
    - the fresh test is level;
    - agreement with the maintainer-approved engine output drops (0.86 →
      0.80);
    - the arbiter was fitted to the current model's probabilities and would
      need refitting.
  - **The maintainer decides.**

### Shipped (2026-10-26)

The maintainer chose to ship the LLM-trained trees, trained on the whole
LLM-labelled corpus plus `synth.py`, and the arbiter was refitted to them.

| | fresh test | gold (out of fold) |
|---|---:|---:|
| previous model + arbiter | 133 | 210 |
| new model + arbiter | **136** | **242** |

With the new model's probabilities the arbiter recovers far more: +23 gold
lines over the model alone, against +16 before.
