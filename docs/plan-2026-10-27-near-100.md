# Plan (2026-10-27): getting provost's success rate near 100%

## Context

The honest success number is not 136/150. That is per-line split agreement on
hand-labelled lines. The whole-capture number on output nobody has tuned
against (`docs/benchmark-2026-10-20-generalisation-round4.md`, 107 inputs) is:

| | PASS | PARTIAL | FAIL |
|---|---:|---:|---:|
| default | **11%** | 48% | **41%** |
| `--multi` | 11% | 60% | 29% |

Rounds 2, 3 and 4 all landed within a few points of this. Two hand-fix rounds,
the tree model, GridNet and 297 generators moved the *seen* sets a lot and the
*unseen* sets not at all. Reaching ~100% is not a tuning problem.

### Why every approach so far stalls

1. **Hand parsers memorise.** Every fix fits the shapes its author saw;
   round N+1 brings new shapes. 265 strategies, ~116 generic, and still 11%.
2. **The gate cannot see "wrong".** Coverage and consistency only warn one
   way. 27 of round 4's 44 FAILs are filed at ≥95% coverage: a prompt, title
   or legend promoted to the header, a wrong split. The gate never fires on
   them, so no fallback (auto-multi, `--model`, `--llm`) ever gets to run.
   **This is the single biggest structural flaw: `--llm` is today a fallback
   behind a gate that misses most of the failures.**
3. **The learned models are data-bound.** Trees plateau at 83% of the
   teacher's per-line splits on unseen families; GridNet at 80%. ~3,000 small
   captures is far too little to learn layout from scratch.
4. **The one thing that is near the ceiling is a frontier LLM reading the
   capture:** 147/150 per line, 286/297 on gold, against a 97% human
   ceiling. It has never been measured whole-capture on a benchmark round.

### The idea that changes the problem

Stop trying to generalise across tools. **Generalise across captures of the
same tool instead**, which is a far easier problem: the layout is fixed, only
the values change. One LLM call per *tool* (ever), producing a deterministic
parser that is stored, reviewable and reused offline. That is `--llm`'s
template mechanism, but it needs three things it does not have yet:

- it must run **first**, not behind the gate (flaw 2);
- it must be **expressive enough** for round 4's largest failure family
  (nested / sectioned records, 17 FAILs), which per-line regexes cannot
  describe;
- it must be **measured** whole-capture on an unseen round, like everything
  else.

Nothing else in the repo has a plausible path to 100%. This does.

## Plan

### Step 1. The decisive measurement: templates on round 4 (no code changes)

Round 4 is unseen by `--llm` (it was written against mcstatus only). Write a
template for each of the 107 round-4 inputs and rate the result on round 4's
own `CRITERIA.md`, against the 12 / 51 / 44 baseline.

- Harness: a scratch script that, per input, runs `template.py learn` (API)
  or, with no key, hands the input + `extract/llm/GUIDE.md` to a Claude
  subagent that iterates `template.py apply` until it covers (as the labelling
  pilot did, `docs/llm-teacher-2026-10-23-pilot.md`). Then
  `provost --llm --sync` with `PROVOST_LLM_TEMPLATE_DIRS=<dir>` into a fresh
  store, and the tidy output is rated. Subagents must not run git.
- Output: `docs/benchmark-2026-10-27-llm-templates-round4.md` with the
  PASS/PARTIAL/FAIL table, and for every non-PASS **why the template format
  could not express it** (that list drives step 2).
- Also record: how many captures exceeded `MAX_LINES`/`MAX_BYTES`
  (`extract/llm/template.py:47`), and the learn-retry rate.

Expected: a large jump on single-shape inputs; the ceiling on nested /
sectioned reports will show the regex format's limit.

### Step 2. Format 2: a parser function, not a regex list

For what step 1 shows regexes cannot express, let Claude write a small Python
parser instead of a template:

- `extract/llm/template.py`: accept `{"format": 2, "tool", "detect",
  "parser": "<python source defining parse(lines) -> blocks>"}`. `blocks` is
  the same structure `apply()` returns today (`name`, `kind`, `records`,
  covered line indexes), so `flat_records`, `write_blocks`, `find` and the
  strategy need no change.
- Run it in a subprocess: `python3 -I` with a 5 s timeout, no network, builtins
  restricted to a whitelist, imports limited to `re`, `json`, `collections`,
  `itertools`. Reject a parser that imports anything else at load time (AST
  walk) before it ever runs. The parser is stored in the user's own store,
  next to the capture, as the templates are.
- `extract/llm/GUIDE.md`: a second section for format 2, with the same value
  conventions, and the rule: write format 1 when it fits; format 2 for
  records that span lines, indented attribute blocks, section titles that
  become a column, fixed-width columns with spaces in values.
- Tests: `ml/tests/test_llm_template.py` (sandbox rejects imports, times out,
  bad return shape; a format-2 parser round-trips through `write_blocks`);
  one shipped format-2 example under `extract/llm/templates/` with a sample
  and golden in `extract/`.
- Re-run step 1's harness on the inputs step 1 did not PASS.

### Step 3. Verify before storing

`learn()` (`extract/llm/template.py:281`) checks only coverage. Add a
**judge** call after a template passes coverage: show Claude the raw lines and
the records the template produced, ask for PASS / PARTIAL / FAIL on the
round-4 criteria plus what is wrong; a FAIL or PARTIAL feeds a third attempt.
Store the verdict in the template (`"judge": "PASS"`). Measure on round 4
whether the judge lifts the rate; keep it only if it does. (Later, the same
judge can rate round 5 automatically, replacing agent self-assessment.)

### Step 4. LLM-first when `--llm` is on

In `provost` (the hook at ~line 1287): when `PROVOST_LLM=1`, a key is present
and no stored template fits, learn a template **before** accepting a generic
parse, not only when the gate holds. Keep the current precedence for
exact-format and tool-specific parsers (`_quality_exempt`): json, csv, a
bespoke strategy for a known tool still win. Replace the generic parse only if
the template's output passes the same gate. Document it in `provost help`,
the man page and the README. Update smoke (`tests/smoke.sh`) for the new
trigger and the still-offline reuse.

### Step 5. Ship a template library (one-time cost)

Run `learn` over `tests/corpus/inputs/` (3,706, one capture per tool) and
rounds 1–4, through the Batches API (`ml/llm/label.py` already has the batch
plumbing), into `extract/llm/templates/`. Gate each template: its output must
pass the quality gate and, where a corpus golden exists, a diff against the
golden is triaged with the LLM labels (`ml/eval/llm-labels-2026-10-23.jsonl.gz`)
as tie-breaker, not accepted blindly. Rough cost at Opus prices and batch
discount: $100–300. Ship as a tarball or gzip the directory if size matters
(`pyproject.toml` force-include).

Then every tool in the corpus has LLM-quality parsing offline, and only
genuinely new tools cost one call.

### Step 6. Round 5

Build, novelty-check and freeze a fresh set (round 4's `novelty.py`,
`manifest.tsv`, `SHA256SUMS` pattern), rate once with the library +
LLM-first on, once default. That is the number to quote.

## What this plan deliberately does not do

- More tree / GridNet training: data-bound, plateaued, cannot reach 95%.
- Another hand-fix round against round 4: that makes round 4 a second corpus
  (`docs/benchmark-2026-10-20-generalisation-round4.md`, "Top failure
  patterns").
- A runtime LLM call per capture: cost, latency, nondeterminism. Per tool,
  once, is the right unit.

## Prerequisite (decided: API key as an environment secret)

The user adds `ANTHROPIC_API_KEY` to the cloud environment's secrets (never
pasted in chat); the session then needs a restart to see it. **No key is in
this session yet**, so execution order is:

1. Now, no key needed: the step-1 harness script; step 2 (format 2 parser
   code, sandbox, tests, GUIDE); step 4 (LLM-first hook, smoke, docs). Each
   committed and pushed on `claude/gracious-darwin-dxgcmu` on top of the
   `--llm` commit (PR #86 stays open; these ride it or a follow-up PR).
2. Step 1's measurement on round 4 runs with in-session subagents writing
   the templates (the labelling pilot's method), one batch per subagent,
   iterating `template.py apply` until coverage passes. Subagents never run
   git. When the key appears (new session), the API path takes over and
   steps 3, 5 and 6 follow.

## Two facts from the corpus scan that shape steps 1 and 5

- The corpus has 3,705 captures, but "one tool, several captures" almost
  always means several *modes* (`kubectl-api-resources`, `kubectl-describe-…`);
  true repeats of one invocation are ~6 files. So a template's unit is
  **tool + mode**, which is what `key()` already does (name or first-lines
  signature), and the library is ~3,700 templates. There is no in-corpus
  test of "template from capture A fits capture B of the same mode": step 1
  must build that from `ml/gen/` (297 generators, fresh values per seed) and
  from the handful of repeats.
- Rounds 2 and 3 have no `gate_held` column; the 38 held captures are a run
  count, not a list. Step 1 rates all 107 round-4 inputs, not just the held
  ones, because 27 of the 44 FAILs were never held.
