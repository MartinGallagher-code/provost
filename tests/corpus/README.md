# Common-tool tidy corpus

A curated corpus of **common Linux tool outputs** plus a batch harness, used to
drive glean toward its design goal: turn any tool output into tidy data with a
**minimum of strategies** — ideally the ~12 generic parsers, no per-tool rule.

- `inputs/<tool>.txt` — a representative captured output for each tool. These are
  the regression inputs; keep them stable.
- `expected.tsv` — the correctness manifest: for each input, the expected tidy
  shape (`table` = strict data-row count, `kv` = key/value snapshot; plus a
  minimum column count).
- `expected/<tool>.tsv` — frozen golden tidy output, written **only** for tools
  that currently come out correctly tidy (so the golden gate tracks the covered
  set exactly).
- `run.sh` — the batch harness (one script, all inputs).

## Running

```bash
bash tests/corpus/run.sh                 # report: full vs --generic winner, tidy? per tool
bash tests/corpus/run.sh --coverage      # markdown coverage table (regenerates COVERAGE.md)
bash tests/corpus/run.sh --golden        # regression: diff generic tidy output vs goldens
bash tests/corpus/run.sh --update-golden # re-freeze goldens for the covered tools
```

**Which tools are covered?** See [`COVERAGE.md`](COVERAGE.md) (generated by
`run.sh --coverage`) for the live ✅/⏳ list.

`run.sh` runs each input through the extract engine in **`--generic`** mode (only
the fundamental parsers) — and, for the report/coverage views, **full** mode too
— then melts the result and checks it against the manifest. The `--generic`
column is the one that matters: it measures how well glean tidies each tool
*without a bespoke strategy*.

**Speed:** inputs are processed in parallel (a job pool sized to the CPU count,
override with `GLEAN_CORPUS_JOBS=N`), and each engine call uses `--emit-meta` so
the wide output and the winning-strategy meta come from one invocation; full mode
is skipped in `--golden`/`--update-golden`. On a 4-core box: report/coverage
~18s, `--golden` ~2.5s (was ~2 min).

## Tested tools & current coverage

**200 tools tested; all 200 tidy — 166 via a generic parser, 34 via a bespoke
strategy.** See [`COVERAGE.md`](COVERAGE.md) for the live per-tool list. (The
first 100 — core sysadmin — plus a second 100 adding git/VCS, language runtimes,
binutils, databases, monitoring, cloud/k8s, and more security/net.)

The last 31 gaps in the second 100 were closed with a handful of format-family
parsers, not one-per-tool: `psql-table` (box tables with `---+---` separators),
`version-string` (`node -v`, `cmake --version`), the monitoring cluster
(`perf-top`/`turbostat`/`slabtop`/`iotop`/`iftop`/`nethogs`, `perf-counters`),
binutils/packages (`objdump-headers`/`readelf-sections`/`ldconfig-p`/`pkg-config`/
`gem-list`/`composer-show`), network/VCS/security (`arp-scan`/`aws-s3-ls`/`host`/
`mtr-report`/`git-remote`/`lastb`/`gpg-list-keys`/`chage-l`), and `text-lines`
(the last-resort one-column dump for ragged text like `strings`).

The generic parsers (led by `aligned-columns` with its header/headerless/two-line
modes, plus `line-records`, `colons`, `yaml`, `key-value`, `equals`,
`indented-hierarchy`, `bracket-log`, `inline-kv`, `labeled-records`, `tree-view`,
`vertical-line`, `psql-table`, `version-string`, and the last-resort `text-lines`)
carry the common 166. The 34 bespoke ones are genuinely idiosyncratic formats —
`mpstat`/`sar`/`pidstat` (sysstat banners), `ping`/`traceroute`/`w`,
`dmidecode`/`lspci`/`uname`/`uptime`, the monitoring cluster
(`perf-top`/`turbostat`/`slabtop`/`iotop`/`iftop`/`nethogs`/`perf-counters`),
binutils (`objdump-headers`/`readelf-sections`), and a handful of
network/VCS/security tools — where a format-family parser is warranted.

The design principle holds: the bulk of common tool output collapses onto a
handful of structural parsers, not one rule per tool. The corpus includes varied
output for the same tool (`free`/`free -h`, `df -h`/`df -i`, `ps aux`/`ps -ef`).

### Not yet tidy — none

All 200 tools are tidy (`run.sh --coverage` shows 0 ⏳). New tools added to the
corpus should first be checked against the generic parsers (`run.sh`); reach for
a bespoke strategy only when the format is genuinely idiosyncratic and no generic
parser produces a correct tidy shape.

Notes: `docker ps` columns are approximate (spaces inside COMMAND/STATUS make
whitespace splitting imperfect); `free`/`ip route`/`lsusb` come out
one-row-per-record with slightly rough column labels but pass the tidy shape
check.

The corpus makes coverage measurable and regression-proof: `run.sh --golden`
diffs each tool's tidy output against a frozen golden, and the full extract
suite (`extract/tests/run_tests.sh`) is kept green through every parser change.
